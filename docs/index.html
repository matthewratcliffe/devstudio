Self-hosted agent console

Your coding CLIs, running as a fleet. One container. Every session in its own checkout.

devStudio drives Claude Code, Codex, OpenCode and whatever else you already have installed — as agents you configure once and then leave to work. Several at a time, each in its own git worktree, on a schedule if you want one.

There is no API integration anywhere. Every agent runs the real CLI as a child process, so the only credential involved is the login you complete in the web UI. Your subscription, your machine, your repositories.

$ docker run -d -p 7080:7080 -v devstudio-data:/data -v devstudio-home:/home/orchestrator ghcr.io/matthewratcliffe/devstudio:latest

Or install it — Windows, macOS and Linux, no container, using the CLI logins already on your machine.

The idea

You are already paying for the good agents. What you are missing is somewhere to put them.

A terminal gives you one agent, in one directory, for as long as you sit there watching it. devStudio gives the same CLIs a place to live: named agents with their own instructions and permissions, conversations that keep running after you close the tab, work that starts at three in the morning because a cron expression said so.

Nothing is reimplemented. When an agent works, it is claude, codex or opencode on a PATH, signed in as you, reading the same files it would read if you had typed the command yourself. That is the whole design: the orchestrator arranges the work and keeps the transcript — the CLI does the thinking.

The parts

What you actually configure

Every noun here is a page in the app, and they compose: an agent belongs to a project, works in a repository, and can be the target of a schedule or one step of a workflow.

Agents

A CLI, a system prompt, a model, a permission mode, and the skills and MCP servers it should have. Any number of them.

Sessions

Conversations that run in parallel up to a cap you set. Each queues its own turns, so you can keep typing while it works.

Guidance

Steer an agent mid-turn instead of queueing behind it — and interrupt the turn in flight if the correction cannot wait.

Projects

Instructions and files every agent in the project inherits, plus the account it signs in with and how long chats get summarised.

Repositories

Clone from the UI, then cut a fresh git worktree per session so concurrent agents never collide in the same checkout.

Workflows

Ordered steps sharing a run context: each finished step publishes its output for every later step to read. Same order runs together.

Schedules

Cron expressions or plain timers, pointed at an agent or a workflow. Unattended runs need no one at the keyboard.

Queues

Give a backlog to an agent and let it drain work with controlled concurrency, retries and usage-limit backoff.

Standards

Global instructions and reference files — setup notes, coding conventions — inherited by every agent and staged into each workspace.

Skills

Reusable instruction files staged into the workspace — write your own, or search the public registry and pull one in with every file it references.

Team settings

One git repository holding the team's agents, workflows, skills, schedules and standards. Every install imports the same definitions; what you made locally is never touched.

Model handover

Open on a strong model and hand over to a cheaper one after a few turns — work the plan out at high effort, carry it out at low.

MCP, both ways

Attach servers to agents, and let agents call back into the orchestrator to read another session, steer a run or start one.

Isolation

Four walls, from the outside in

Agents run commands, so the question is not whether to trust them but what each layer is allowed to reach. Every session gets its own worktree, which is what makes running four at once safe rather than merely fast.

Permission modes go from asking about everything, through read-only planning, to editing freely — with the last one meant for a worktree you are willing to throw away.

container — the CLIs, their logins, one volume
project — instructions, files, account
worktree — one per session, cut from a branch
permission mode
ask · plan · accept edits · no restrictions

Providers

Anything you can already run

Two are built in because their output shapes are fiddly. Everything else is described on a form — executable, arguments, how it prints — and becomes an agent provider with no code change.

Claude Code
Streams token by token, with tool calls and their durations in the transcript. Signed in through the browser, device code or a pasted token.
OpenAI Codex
Same treatment, including resuming a conversation across turns and reporting what each command did.
OpenCode
The OpenCode npm CLI is available as a first-class provider, with configurable executable and model settings alongside the other built-in agents.
Any installed CLI
Copilot, Gemini, Cursor — give it an argument template and tell it where the answer is in the output.
ACP agents
Agent Client Protocol over stdio: the agent brings its own tools and asks before using them, and the answer comes from the session's permission mode.
llama.cpp and friends
Any OpenAI-compatible endpoint. A bare model has no tools, so devStudio runs the loop itself — reading, writing and running commands in the workspace on the model's behalf.

Desktop

Or no container at all

Docker is the answer on a server. On your own machine there is a second build: an installed app with no volumes and no bind mounts to configure, because agents reach your files by simply being you. It signs in with the ~/.claude and ~/.codex logins already on the machine, browses every drive you have, and updates itself in the background — the new version is waiting the next time you quit.

Windows x64 Per-user, no administrator. Adds the WebView2 runtime if Windows lacks it, and a tray icon so closing the window leaves the agents running.

macOS WKWebView, and a universal build for each architecture. No tray — closing the window stops the server with it.

Linux x64 An AppImage — chmod +x and run. Needs WebKitGTK: sudo apt install libwebkit2gtk-4.1-0 on Debian and Ubuntu.

Every link is the latest release — all assets, including portable builds. It is the same application either way: a small shell starts the exact binary the container runs on 127.0.0.1 and shows it in the system web view.

The sandbox row is the one to read twice. In the container, an agent that runs something reckless wrecks a container. On the desktop it is running as you, with your files and your credentials.

Install

One container, two volumes

State is JSON on a volume — no database, and a volume backup is the whole backup. The second volume holds the CLI logins, so you sign in once and it survives upgrades.

Images are published for amd64 and arm64 on every push to the default branch. Then open http://localhost:7080 and sign in from the Logins page. 

# docker-compose.yml
services:
  orchestrator:
    image: ghcr.io/matthewratcliffe/devstudio:latest
    ports:
      - "7080:7080"
      - "1455:1455"   # Codex browser sign-in only
    volumes:
      - devstudio-data:/data
      - devstudio-home:/home/orchestrator
    restart: unless-stopped

  devstudio-data:

Contributing

Take it apart

This is one person's tool that turned out to be worth publishing. If it is nearly what you want, the gap is probably small — and the parts most people need to change are the ones deliberately left soft.

Adding a CLI is a form, not a patch. A skill registry, a source-control host and an agent provider are each an interface with an implementation beside it to copy. And if you would rather not wait for an opinion, fork it — it is MIT licensed, and nothing here expects to be the only copy.

Report something A bug, a CLI that does not fit the provider form, a workflow the scheduler cannot express. Failure cases are the useful ones. Fork it MIT, so use it however you like. Build, test and run it locally with the .NET 10 SDK and Docker; the README covers the layout and where each seam is. Open a pull request CI runs the tests on every branch. Small and self-contained lands fastest; open an issue first if it is large.
